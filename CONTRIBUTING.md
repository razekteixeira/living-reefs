# Contributing to Living Reefs

Thanks for helping. Issues, ideas and pull requests are all welcome. Please follow the
[Code of Conduct](CODE_OF_CONDUCT.md), and report security problems privately as described in
[SECURITY.md](SECURITY.md).

## Setup

- JDK 25 (any distribution). Gradle comes with the wrapper.
- No Minecraft account is needed: Loom downloads the game for development.

```bash
./gradlew build              # compile + unit tests + server GameTests
./gradlew runServer          # dev server in ./run
./gradlew runClient          # dev client (offline account)
./gradlew runClientGameTest  # real client; regenerates screenshots, opens a window
```

## Layout

| Path | What lives there |
|---|---|
| `src/main/java/.../core` | Pure logic with no Minecraft classes: species pairing (`SpeciesTable`), reef health and actions (`ReefRules`), where coral spreads (`SpreadPlanner`), settings. Unit tested. |
| `src/main/java/...` | Thin Minecraft layer: the random tick mixin, `ReefTicker`, reading conditions and blocks from loaded chunks only, tags, game rules, commands, config. |
| `src/main/resources/data/livingreefs/tags` | Default block and biome tags; datapacks can change them. |
| `src/test` | JUnit tests for `core` and config loading. |
| `src/gametest` | Server GameTests (`LivingReefsGameTests`, with test environments in `resources/data/livingreefs-gametest`) and the client capture (`client/LivingReefsCaptures`). |
| `tools/` | `benchmark.sh` (dev server cost measurement), `mutation.py` (mutation check), `rcon.py`. |
| `docs/` | Research report, specification, gate log. |
| `site/` | GitHub Pages site. `branding/` holds the artwork scripts and the CurseForge copy. |

## Rules for changes

- **Every behaviour change comes with a test that would fail without it.** Prefer `core` unit tests;
  use a GameTest when real blocks, biomes, random ticks or commands are involved. Tests that change
  global state (game rules, config) run in their own test environment.
- **Tests must have teeth.** `python3 -P tools/mutation.py` plants known faults one at a time and
  checks a named test fails for each; a compile error never counts. Add a mutant when you add a rule.
- **Performance:** the handler runs on coral random ticks on the server thread. Roll the chance
  first, read the world only after, never load a chunk (read through `WorldReefView`). If you touch
  `ReefTicker`, `ReefConditions` or `SpreadPlanner`, include `tools/benchmark.sh` numbers from
  before and after.
- **Server-side only:** no new blocks, items, packets or synced registries, so vanilla clients keep
  working. Game rules are fine (the vanilla client ignores rules it does not know).
- **Never replace a block that is not water** when growing, and never revive dry dead coral.
- Code style: tabs, and match the surrounding code. Comments explain why, not what.

## Pull requests

1. Open an issue first for anything bigger than a bug fix, so we can agree on the approach.
2. Keep the PR focused, run `./gradlew build`, and fill in the template.
3. If chat output changes, regenerate the media and update the chat panel text in
   `site/index.html` and the sample in `branding/curseforge-description.md` from the same run's log
   (see "Artwork" below).

## Benchmark

`tools/benchmark.sh` starts the dev server (port 25566, RCON on 127.0.0.1:25576 with a random
password), builds a 64 x 64 warm-ocean reef of 8,192 coral, and reads the handler's own time per
second from `/reef stats`: 40 s warm-up, then 15 readings at `random_tick_speed` 3 and at 300.

## Artwork

Everything is generated by scripts, so it can be redone after any change:

| Script | Produces |
|---|---|
| `caffeinate -dimsu ./gradlew runClientGameTest` | Real client captures in `build/run/clientGameTest/screenshots`, plus the "[reef survey]" light line in the log (macOS: `caffeinate` stops display sleep from stalling the window) |
| `branding/make_media.sh` | `site/media` screenshots, gallery shots and the time-lapse GIF |
| `Blender -b -P branding/render_logo3d.py -- branding/logo3d.png` | The 3D voxel logo, rendered from the icon's own pixels |
| `python3 -P branding/make_banners.py` | `banner.png`, `social.png`, `readme-header.png` |
| `python3 -P branding/make_icon.py` | The pixel icon at every size |

## Releases (maintainers)

Living Reefs is published on CurseForge. The one-time project setup (page, logo, gallery, token,
project ID) is in [`branding/curseforge-listing.md`](branding/curseforge-listing.md).

1. Move the `Unreleased` notes in `CHANGELOG.md` under the new version and set `version` in
   `gradle.properties` (`-alpha.N` / `-beta.N` / `-rc.N` suffixes pick the CurseForge release type).
2. Join a dev server with an **unmodified** 26.3 client (`./gradlew runServer`, then a vanilla
   launcher profile) and check `/reef check`, `/gamerule livingreefs:coral_growth` and a growing
   reef. This is the one check no automated test covers.
3. Tag `vX.Y.Z` and push the tag. The release workflow builds, runs every test, creates the GitHub
   release and uploads to CurseForge when the `CURSEFORGE_TOKEN` secret is set and
   `curseforge_project_id` is filled in.
4. `./gradlew publishCurseforge` without a token is a dry run: it assembles the upload under
   `build/publishMods/` without sending anything.

The CurseForge token can upload files to the project, so keep it out of reach of other workflows:
the safest place is a `release` environment that only allows `v*` tags (and, if you like, needs
your approval), with `environment: release` added to the release job. The build workflow never sees
it, and the release workflow only hands it to the publish step.
